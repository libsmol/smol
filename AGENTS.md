# AGENTS.md

These rules apply whenever you write code, review code or change prompts in this repository.

## Project

A Rust workspace (edition 2021) whose code from the model runs in a pinned CPython.

- `crates/libsmol`: the ACP agent library and the `libsmol` binary. `acp/` speaks ACP and manages sessions (serve reads and writes; rpc sends and receives JSON-RPC; session runs one task per session, and while a turn is in progress it only takes finished titles, so option changes, MCP toggles and the next request all wait for the turn to end; servers manages a session's MCP connections; translator turns agent events into ACP messages). `agent/` works through a task step by step (step, compact for compaction, delegate for `agent()`: each task gets a new worker and `Agent::run`, with the model and description of the role named for it, at most 8 at a time per session, the agents it starts get no `agent()` themselves, and their records are saved in the call's result for replay but never sent to the model). `worker/` is the agent's side of the worker: `host.rs` manages it, `mod.rs` is the message protocol both sides share, `python.rs` installs the Python it runs, and `sandbox.rs` confines it. `spawn.rs` starts the worker and `!` commands in process groups and clips their output. `config/` reads the configuration, and `config/setup.rs` is `libsmol setup`, the interactive wizard that writes `model.toml`. The Rust code the builtins call (ls, grep, fetch, view) and the MCP client live in `tools/`, and `guest` in `lib.rs` exports what `crates/worker` builds on. Each session has one worker: CPython 3.14 from python-build-standalone, the same pinned build with its checksums on every machine. Opening a session installs what is missing before the sandbox is made: it downloads the runtime, precompiles it and the worker module of its own version into `<config>/runtime`, and holds them and the venv with shared locks in `<item>.lock` next to each, so a libsmol of another version removes only what no session holds, and a venv goes once no session holds it and the working directory its lock names is gone. The worker is the runtime's own interpreter, started with `-I -S -B -X utf8` to load `_smol` and call `serve()` with the interpreter of the venv kept for the working directory in `<config>/venvs/<runtime>`; `serve()` confines itself, sets `sys.executable`, `sys.prefix` and `sys.exec_prefix` to the venv, then runs site. The code can write the venv, so nothing in it runs before the sandbox holds and the agent never reads it: `_smol.renew` makes it anew under the same sandbox when its `python` or `pip` is missing. Tests use a runtime and venv under `target/<profile>`. `worker/sandbox.rs` builds its command with a cleared environment (a short list plus `[allow] env`, with the venv first on `PATH` and in `VIRTUAL_ENV`). On Linux a Landlock ruleset and on macOS a Seatbelt profile, which `_smol` applies to its own process with `sandbox_init` before anything else runs, let it and every program it starts write only to the session directory, the venv, its own `TMPDIR` and the copies folder (plus `[allow] write`), connect only to Unix sockets in those places, signal only inside the sandbox, and hide the credential locations, the config directory (except the copies, skills, the runtime, the worker module and this venv) and `[deny] read`; everything else stays readable, the network is open and there are no permission checks. Windows and kernels without Landlock get no file isolation, which only the log records. The sandbox and its temporary folder live as long as the session, across worker restarts. There is no memory snapshot: when the worker restarts its variables are gone, and the model is told before its next code.
- The worker channel: the agent listens on a loopback address and passes the address and a token to the worker in `SMOL_CONTROL`. Messages in both directions go line by line over that TCP connection, all shaped like JSON-RPC (requests, replies and notifications; cancelling is a `cancel` notification). The worker's stdout and stderr share one pipe, and both are the code's output. After each snippet finishes, and before reporting back, the worker writes an `END` marker; only output before the marker belongs to that snippet. While code runs, the clipped output is forwarded to the client every 100 ms. Output sent to the model has terminal escape sequences removed, and progress redrawn with `\r` keeps only its last frame per line. `view()` is handled by the worker itself: it detects the format, writes a copy into the directory given by `SMOL_COPIES`, then sends a notification without waiting for a reply. The code runs in the worker's process and can write to its connection too, so the agent, which runs outside the sandbox, takes only a bare file name in the copies folder from that notification and reads a copy only when it is a plain file with one link. On interrupt the worker's listener thread sends `SIGINT` to the main thread, which runs the code (on Windows it only sets the interpreter's interrupt flag); the agent resends it every 500 ms and kills and restarts the worker if it hasn't stopped after 3 seconds.
- `crates/worker`: the `_smol` Python extension module, package `libsmol-worker`, which is not published. It is the worker's side of the channel and the Rust half of the builtins, written in `bootstrap/`, where builtins, mcp and run execute in that order in one set of globals. PyO3 targets the stable ABI without asking any Python (`PYO3_NO_PYTHON` in `.cargo/config.toml`). Releases attach it as `smol-worker-<target>`, which libsmol downloads for its own version and checks against `SHA256SUMS`, and `build.sh` installs it into `~/.smol/runtime`.
- `crates/smol`: the ACP client and the `smol` binary, published as the `libsmol-tui` package. It is TUI only and exits with an error outside a terminal. `chat::Session` holds the protocol side of a session's state, and `tui/` only handles display and input. It reads no configuration, starts the `libsmol` next to it, and falls back to PATH when there is none. When the first session can't open with -32000, it runs the agent's terminal auth method in the terminal before entering the TUI, then retries once. Input starting with `!` goes through `_smol/shell`: the agent runs it with the user's `$SHELL` (cmd on Windows) in the session directory, and programs left in the background end with the session. It is recorded as `MemoryStep::Shell` and sent to the model as a user message in the next turn. Like colon commands, it queues until the current turn ends. Agents that `agent()` starts arrive as tool calls marked `_smol/agent` whose `parent` is the call running that code and whose `rawInput` holds their task, role and name, and the TUI groups them under it. All TUI colors are in `tui/theme.rs` (Dracula). On entry the TUI replaces the terminal's default foreground and background and sets a steady cursor, and it restores them on exit. Every frame is wrapped in synchronized output, and terminals that don't report truecolor get 256 colors.
- `crates/reaper`: the watchdog and process groups, published as the `libsmol-reaper` package and still imported as `reaper`. However libsmol dies, the programs it started (the worker, MCP servers, `!` commands) are killed as whole groups. Programs that start a new session (`setsid`, `start_new_session`) leave the group; they are found in /proc by the `SMOL_REAPER` mark they inherit, which only works on Linux. Windows has no process groups: each program is started suspended, put in a Job Object that kills everything when its handle closes, then resumed, with no watchdog. Lookup of `.cmd` commands such as `npx` lives here too. Functions both smol and libsmol need also live here (system error text in `cause` and `described`, `terminal_view` for removing terminal escape sequences and keeping the last frame of `\r` redraws, `tilde` for writing the home directory as `~`), because smol must not depend on libsmol.

## Process

1. Look at the flow and the data first, not the files. Follow the data from a prompt coming in to the answer going out, and look for detours: one thing with two representations, two places that parse it, a layer that only forwards.
2. For a large change, write the complete plan first and start only after it is approved. The plan states the invariants (features, the shape of ACP messages, the text sent to the model), what changes and what gets deleted.
3. A claim of "no behavior change" must be proven with a black-box baseline diff: drive it with a mock model server, record the ACP message stream and the full text sent to the model, and capture the TUI with tmux screenshots. Every difference must be one the plan lists.
4. Work in phases, and at the end of each phase run `cargo fmt`, `cargo clippy --all-targets`, `cargo clippy --workspace --all-targets --target aarch64-unknown-linux-gnu` and `cargo test --workspace`.
5. The order is design refactoring, then a line-by-line readability rewrite, then cleaning up comments and tests. Done in reverse, the work gets thrown away.
6. Finish with a real model. Use deepseek for simple tasks; for long context, lower `context` in model.toml so compaction actually triggers. If the TUI changed, check it with tmux screenshots.
7. After changing code, run `./build.sh` to install into `~/.local/bin` (`build.ps1` on Windows), or the user won't get the change. Keep build output in the project's `target/`; don't point `CARGO_TARGET_DIR` at `/tmp` (it is a RAM disk).
8. Commit or push only when the user asks.

## Design principles

- Less code comes from putting responsibilities in the right place and deleting duplication, not from squeezing the formatting: don't widen rustfmt, don't cram expressions together, don't remove the blank lines between logical steps, don't add a flag to save a branch.
- Do each thing in one place: one parser, one representation, one error message. Prefer fewer, cohesive modules with short names free of any language's flavor.
- Put logic in the right layer. smol does not depend on libsmol, and `_smol/` extensions are added only when ACP isn't enough. A `_smol/` name means exactly one thing: the method, the marker on standard messages and the advertised capability share that name, and a key's value type never changes. Data fields use camelCase like ACP. Every `_smol/notice` carries `step` (it belongs to the step in progress) and `unsaved` (a save failed).
- libsmol reads all configuration (`model.toml`, `roles.toml`, the `[mcp.*]`, `[allow]` and `[deny]` tables in `agent.toml`) each time a session opens, so `:new` picks up changes. `libsmol setup` is the only thing that writes `model.toml`, and the format lives next to its parser in `config/`. A session that can't open for lack of `model.toml` fails with -32000 (auth required), and clients that declare ACP terminal authentication are offered `libsmol setup` as the auth method. When a session opens it also reads `AGENTS.md` (or `CLAUDE.md` when there is none) from the config directory and from every directory from the root down to the working directory, and appends them to the system prompt; files that can't be read are skipped with a notice. Skills are read at the same time: one `SKILL.md` per folder under `skills/` in the config directory and under `.smol/skills/` at every level, with deeper ones winning on a name clash. The prompt lists only `name` and `description` from the front matter plus the file path, and the model reads the file when it needs it. Roles come the same way from `roles.toml` in the config directory and `.smol/roles.toml` at every level; a role whose `model` isn't in `model.toml` is skipped with a notice, and without roles the worker (told by `SMOL_AGENTS`, which workers of agents that `agent()` starts don't get) leaves `role` out of `agent()`'s signature.
- Context in a prompt arrives as ACP resource links or embedded text, and libsmol declares embedded context so editors send what they show, unsaved edits included. A `file://` link or embedded file becomes a file attachment, read when the task starts unless its text came along, and a `#L10:20` fragment keeps only those lines. Embedded text for anything else goes to the model as `<resource uri="…">`, and other links stay in the task text.
- Errors read `label: object: problem`, all lowercase, with no trailing period. Text for people uses `Display`; text for the model lives in `prompt.rs`.
- Logs are English, one line per event, shaped `domain[qualifier]: event[, detail][ [key=value, ...]]`, lowercase with no trailing period. Lines from a session carry its id through the session's span. An error is logged once, where it ends the work it belongs to.
- Never write compatibility logic for one particular model; solve problems in the prompt or the protocol.
- Code runs only through native tool calls. Step requests declare a single `eval(code)` tool, the prompt only describes that tool, a reply without a call is the answer, and code blocks written in the message text are not run. When the tool is named `code`, models often send calls without arguments. The tool description doesn't mention tags; if it did, models would write the tags into the arguments. A call whose only argument is a string is treated as code even if that argument isn't named `code`. One reply can contain several calls; they run in order once all have arrived, and after one fails or is interrupted the rest don't run. Every call gets a reply, calls that didn't run say why, and `tool_call_id` matches each reply to its call. Calls with no readable code (another tool was called, or the eval arguments hold no code or only tags) stay in the history but don't run; they count as errors and their reply says why. Their arguments are always sent back as `{}` and characters the server rejects in tool names are replaced with `_`, so the bad content is never echoed and the server doesn't reject the request. Unreadable eval calls are mostly transient glitches, so the reply is first regenerated silently, up to 3 times, without using up error retries; only after that does each call get such a reply. In the history the code is the `tool_calls` on the assistant message, and results and errors are the `tool` messages replying to them. Images can't go in `tool` messages: once all replies of the step are sent, they go at the start of the next user message, or in a new user message when none follows, because the server rejects them in between. Call ids are numbered `call_N` in order of appearance and never change when later steps are added, which keeps the prompt cache matching. Calls in a stream arrive one after another, and each is handed over when the next one starts; once all calls have arrived, it doesn't matter how the stream ended. When the closing tags at the end of the code run past 256 tokens, the request is cut off and the code runs as usual (the worker strips the tags), and that step has no usage. Some models keep repeating closing tags after the code, and without the cutoff they would run to the output limit.
- The output limit is set per model with `max_tokens` in model.toml, and the provider's default applies when it is unset. deepseek counts reasoning toward it, so a small value can cut a reply off mid-reasoning. Truncated replies don't go into the history, and when the worker repairs code it keeps a copy of the original (`unrepaired`), which is not sent to the model either.
- Images and videos are enabled per model with `image` and `video` in model.toml. Whatever the current model doesn't accept is replaced with a one-line note, so the history still sends after switching models. When the model accepts neither, the system prompt doesn't list `view`, and calling it only returns that note.
- These are deliberate and must not change: the worker has no permission prompts and no network limits, there is no maximum step count, and code execution has no timeout (the user interrupts).

## Code rules

1. Code used once is not split into a function; write it where it is used so it reads top to bottom. Exceptions: trait implementations, cross-module or public APIs, recursion, functions passed as values, pure functions with their own unit tests, and helpers shared by several tests.
2. Don't pass call results or long expressions directly as arguments, as in `f(g(x), h(y)?)`; bind them to named locals first. Exceptions: constructing types and enum variants, and wrappers like `Box::new`/`Arc::new`, may be arguments or wrap a call directly; test helpers that build data, and accessors and conversions (`to_owned`, `join`, `clone` and the like), may be arguments; assert macros are exempt.
3. Leave a blank line between logical steps (setup, work, cleanup, return), and keep line length and density even.
4. Names have at most 3 words: functions, types, fields, constants and test names alike. Upper limits are `MAX_*` and lower limits `MIN_*`, with `_BYTES`, `_CHARS`, `_LINES` or `_ROWS` appended for units; waits and timeouts are `*_WAIT` and intervals `*_EVERY`; names that mirror a third-party library's parameters follow the library.
5. Always `use crate::...`, never `use super::`, in test modules too. Prefer `pub(crate)`. Don't write multi-segment inline paths in code (`std::mem::take(..)`, `crate::history::new_id()`); a single module prefix (`fs::write`, `env::var_os`) is fine.
6. Don't pass multi-line or nested closures to `map`/`map_err`/`and_then`/`ok_or_else`/`filter_map`. Use `match`, `let … else` or `for` instead, or name the mapping function first: `let failed = |e| …; .map_err(failed)?`.
7. Read each file in full before changing it, and make every change by hand, never with regex or batch replacement.
8. Check Unix and Windows `cfg` branches together; both targets must compile and be clippy-clean.

## Comments

- Write a comment only when deleting it could let a later reader silently break something: a hidden technical constraint (a panic, disk or API format compatibility, signal or thread semantics, an ordering a refactor could easily lose, a regression hit before, an ownership convention for callers).
- Don't write product or behavioral rationale, and don't write docs that restate a name, a signature or a module's purpose. If a name can say it, let the name say it.
- Write in English: one short sentence in plain, idiomatic English, starting with a capital letter and without a trailing period. Don't chain clauses with colons or semicolons, don't narrate purpose ("so that ..."), and don't paste examples.
- Use `///` on items and `//` inside function bodies. The same rules apply to Rust and to the embedded Python (`#`).
- Comments and tests the user deleted were deleted on purpose; don't add them back.

## Tests

- Tests always live in `#[cfg(test)] mod tests` inside the source file, never in a separate tests.rs. Shared helpers go in the parent module's `mod tests` as `pub(crate)`. Python helper scripts are the exception.
- Test names have at most 3 words. Assert messages print only values (`"{logs}"`), never sentences, and `expect` texts are short ("evaluate", "error").
- Test data is English. Bugs that use byte indices as character counts only show up with multibyte text, so data that goes through text handling includes accented words (café, naïve, résumé) and, where display width matters, emoji (🐍). The only Chinese in the repository is the full-width punctuation the code recognizes in model replies (such as '。' and '：') and the tests of that handling.
- Tests start real workers: the runtime is downloaded once into `target/<profile>/runtime`, one venv in `target/<profile>/venvs/venv` serves them all, and the module is the `lib_smol` that `cargo test --workspace` built in `target/<profile>/deps`; tests never download a released one. Worker-side code is built without `cfg(test)`, so its test-only limits don't apply there.

## Text for the model (prompts, builtin docs, errors)

- Priorities: accuracy first, then rules that make the model smarter, brevity last.
- Don't mention things the model shouldn't use. Whatever gets mentioned, the model drifts toward.
- Review each piece of text on its own first, then review the complete prompt as actually assembled.
- Output in examples must be captured from real runs. Builtin signatures must be exact and complete.
- After changing a prompt, test it with deepseek, and compare old against new when in doubt.

## Safety and configuration

- Don't change the user's real configuration (`~/.smol/`) without their consent.
- Don't print secrets: the Authorization/Cookie headers in `agent.toml` and the API keys in `model.toml`.
- When testing with a real model, copy the configuration into a temporary directory (`SMOL_CONFIG_DIR`), don't print its contents, and delete it right after. Don't write test sessions into the user's real history. The sandbox leaves the network open and most files readable, so never give a real model tasks that need accounts or secrets.
- In shell, `rm` of a variable path must be written as `"${VAR:?}"`.

## Lessons learned

- Edition 2021 has no let chains; use nested `if let` or `let … else` instead.
- A closure stored in a local and then passed as `dyn FnMut(Event)` needs its parameter type annotated (`|event: Event|`).
- Parts of rmcp's error chain don't set `source`; link them by type, then reuse `http_cause` to get the real cause.
- Python runs signal handlers only on the main thread, so the code runs there and the listener thread interrupts it with `pthread_kill`, which also wakes waits on locks (`queue.get`, `Event.wait`). A long call inside a C extension that never checks signals can't be woken, and neither can most blocking calls on Windows; the only way out is the agent killing the worker.
- glibc's `system()` makes the whole process ignore `SIGINT` while it waits for the child, so `os.system` can't be interrupted, and after 3 seconds the worker is killed and every variable is lost. Interrupting `subprocess.run(..., shell=True)` kills only `sh`; the command it started is orphaned and keeps running in the worker's group until the worker is killed or the session ends.
- The worker writes `END` before reporting in, and the agent counts it as started only after receiving both. Without this step whatever starting up prints, such as warnings from site, would count as output of the first snippet.
- While a builtin waits for the agent's reply it must release the GIL with `py.detach` and call `py.check_signals` every so often, or it can't be interrupted. The worker also waits for the next message without the GIL, so threads the code started keep running between snippets.
- `cargo test` builds a library only for doc tests and builds those only from an rlib, so `crates/worker` has the rlib type to keep the module tests load fresh, and only `cargo build` copies it up out of `deps`. A test binary of the crate would leave the Python API unresolved, so it has none, and macOS links the module only with the `-undefined dynamic_lookup` its build script adds.
- A venv's own interpreter and `pyvenv.cfg` are files the code can replace, and on macOS the sandbox holds only once `_smol` runs, so the worker starts the runtime's interpreter and becomes the venv in-process. `venv` writes `pyvenv.cfg` before it finishes, so a venv counts as complete once it has `pip`, which the agent only looks up without reading or following; one that isn't is made anew with `--clear`, which empties the folder in place and so keeps its Landlock rule.
- A lock file is never removed, since a session may hold the one it opened while another removes the path and makes a new file there. The runtime is unpacked inside the store and renamed into place, because a rename moves a folder only within one file system.
- PyO3 turns `PathBuf` into `pathlib.Path`, so builtins return `OsString` where the code expects `str`.
- C extensions print through C's stdio, which holds what goes to a pipe until flushed, so the worker flushes it before every `END`.
- Proxies silently close idle HTTP connections, and the worker's tokio runtime only runs during calls such as builtins, so it never sees the close and reusing the connection fails. Every HTTP client goes through `utils::http_client`, which disables connection pool reuse (`pool_max_idle_per_host(0)`).
- Landlock can only grant, never take access back below a granted folder, so a folder holding a hidden path is granted entry by entry (`spread`). Its rules hold the inodes that existed when the session opened: the copies folder is made then and removed only when the sandbox drops, and a file replaced in a spread folder becomes unreadable.
- Seatbelt takes the last matching rule and compares real paths (`/private/tmp`, not `/tmp`), so the profile is ordered by depth and every path is canonicalized.
- `sandbox_init` is deprecated, so it is looked up with `dlsym`: linking to it would keep libsmol from loading at all on a macOS without it, while a missing one only leaves the worker unconfined. `_smol` reads and removes `SMOL_SANDBOX` and applies the profile before any other thread starts, so neither the code nor the programs it starts see the profile. Python starts without site (`-S`), and `serve()` runs site only after that and after setting `sys.prefix`, because site runs the `.pth` files of the venv and reads `sys.prefix` when imported.
- Landlock counts connecting to a Unix socket as a write right (ABI 9, Linux 7.1), and signals and abstract sockets are scoped from ABI 6 (Linux 6.12). Older kernels drop what they don't know and the rest of the ruleset still holds, so the log names what stays open. Seatbelt checks a Unix socket by its path under `network-outbound`, and names resolve through `/private/var/run/mDNSResponder`.
- The Landlock `pre_exec` runs after fork in a multithreaded process, so it only calls `prctl` and the raw `landlock_restrict_self` syscall, with the ruleset built beforehand in the parent.
