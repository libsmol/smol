# AGENTS.md

These rules apply whenever you write code, review code or change prompts in this repository.

## Project

A Rust workspace (edition 2021) whose code from the model runs in a pinned CPython linked into libsmol.

- `crates/libsmol`: the ACP agent library and the `libsmol` binary. `acp/` speaks ACP and manages sessions (serve reads and writes; rpc sends and receives JSON-RPC; session runs one task per session, and while a turn is in progress it only takes finished titles, so option changes, MCP toggles and the next request all wait for the turn to end; servers manages a session's MCP connections; translator turns agent events into ACP messages). `agent/` works through a task step by step (step, compact for compaction, delegate for `agent()`: each task gets a new worker and `Agent::run`, with the model and description of the role named for it, at most 8 at a time per session, the agents it starts get no `agent()` themselves, and their records are saved in the call's result for replay but never sent to the model). `worker/` holds both ends of the worker: `mod.rs` is the message protocol they share, `host.rs` is the agent's end and manages the worker, `guest/` is the worker's end, which runs inside the sandbox with the code, and the Rust half of the builtins, whose Python half is in `guest/bootstrap/`, where builtins, mcp and run execute in that order in one set of globals. `venv.rs` holds the working directory's venv and decides when it goes, `workplace.rs` is what a session's workers share (its folder, copies, venv and sandbox) and decides what the code may write, read and never see, `sandbox.rs` enforces such rules without knowing what the paths are, and `host.rs` starts the worker in the workplace. The session's first worker chooses each MCP server's name in code, and later workers get that name with the server, as those of agents that `agent()` starts lack builtins it was chosen to avoid. `spawn.rs` starts the worker and `!` commands in process groups and clips their output. `config/` reads the configuration, and `config/setup.rs` is `libsmol setup`, the interactive wizard that writes `model.toml`. The Rust code the builtins call (ls, grep, fetch, view) and the MCP client live in `tools/`. `tools/memories.rs` keeps the memories of `remember()`, `recall()` and `forget()` in SQLite at `<config>/memory.db`, each for its working directory as `utils::folded` spells it or for every directory; the code can't reach the config directory, so the worker sends those calls over the channel. `host.rs` answers only the calls to the MCP servers it installed and hands the rest, these and those of `agent()`, to the agent's `serve`, which refuses all but `recall` to agents that `agent()` starts. Clients list the memories a session sees and forget one through `_smol/memories` and `_smol/forget`, which `serve` answers on a task of its own, because the session task would hold them until the turn ends while smol waits for the reply. FTS5 indexes each memory by words: jieba cuts the Chinese for search, which also gives the shorter words inside long ones, and the rest goes to FTS5's own tokenizer. A query is any of its words, each quoted, ranked by bm25. When a session opens it reads the newest global memories, how many there are and how many its directory has into `agent::Brief` with its instructions and skills, and the agents `agent()` starts get the same, so the system prompt never changes during a session and the prompt cache keeps matching. Each session has one worker: libsmol's own executable, with the CPython 3.14 that `crates/worker` links in, started from the file `worker::program` names with `--worker <venv>` (on Linux `/proc/self/exe`, which still runs this libsmol after an update replaced the file) and isolated, writing no bytecode and in UTF-8 mode, as `-I -B -X utf8` would make it. `--worker` is told apart before names. Started under a name a venv gives its interpreter (`python…`, `𝜋thon`), libsmol runs as that python, so a venv's `bin/python3` links straight to libsmol, and `worker::enter` relinks it when libsmol has moved. Windows extension modules import CPython by the name `python314.dll`, so there every Python process runs from a hard link of libsmol by that name in the config directory, which `worker::program` keeps current beside pbs's `python3.dll` forwarder, and the loader binds their imports to the running program. A Windows venv's `Scripts\python.exe` is a hard link too, which relays to the `python314.dll` its `pyvenv.cfg` names; `stdlib.py` makes it so for every venv, and `enter` relinks it and points `sys._base_executable` past it for multiprocessing. In libsmol `crate::worker::…` is the module and a bare `worker::…` the crate, except at the crate root, where the module wins. `history.rs` saves each working directory's sessions, with their copies, in a project folder of their own, `<config>/projects/<name>-<hash>` after the directory as `utils::folded` spells it, and a session opens only in its own directory. Opening a session holds the venv kept for the working directory in `.venv` in that folder, with a shared lock in `.venv.lock` next to it that names the directory, so a venv goes once the directory is gone and no session has used it for a week, and the folder goes with it once nothing else is in it. A load is checked against the folder before the open session with that id closes, since a saved session never moves. `serve()` takes what the code must not inherit, then `worker::enter` makes the venv, or adds what it lacks while keeping its packages, when its `python` or `pip` is missing, holding `.lock` in it since other agents and sessions in the directory may be entering it too. It then puts the venv first on `PATH` and in `VIRTUAL_ENV`, sets `sys.executable`, `sys._base_executable`, `sys.prefix`, `sys.exec_prefix` and `site.PREFIXES` to it and runs site again. The code can write the venv, so nothing in it runs before the sandbox holds and the agent never reads or follows anything in it. A venv's packages are built for one kind of machine, so one config directory serves one kind of machine. Tests share the venv `target/<profile>/.venv`. `worker/sandbox.rs` builds its command with a cleared environment (the names its rules pass, which `workplace.rs` makes a short list plus `[allow] env`, and while the sandbox holds, pip's cache in its `TMPDIR`). On Linux a Landlock ruleset and on macOS a Seatbelt profile, which the worker starts under through `sandbox-exec`, let it and every program it starts write only to the session directory, the venv, its own `TMPDIR` and the copies folder (plus `[allow] write`), connect only to Unix sockets in those places, signal only inside the sandbox, and hide the credential locations, the config directory (except the copies, skills and this venv) and `[deny] read`, of which Linux still lets the code list the names; everything else stays readable, the network is open and there are no permission checks. Windows and kernels without Landlock get no file isolation, which only the log records. The sandbox and its temporary folder live as long as the session, across worker restarts. There is no memory snapshot: when the worker restarts its variables are gone, and the model is told before its next code.
- The worker channel: the agent listens on a loopback address and passes the address and a token to the worker in `SMOL_CONTROL`. Messages in both directions go line by line over that TCP connection, all shaped like JSON-RPC (requests, replies and notifications; cancelling is a `cancel` notification). The worker's stdout and stderr share one pipe, and both are the code's output. After each snippet finishes, and before reporting back, the worker writes an end marker made from the token on its own copy of the pipe; only output before the marker belongs to that snippet. Every call the worker makes gets a reply, also one from a thread the code started that a snippet's end stops or that arrives while an MCP server is added. While code runs, the clipped output is forwarded to the client every 100 ms. Output sent to the model has terminal escape sequences removed, and progress redrawn with `\r` keeps only its last frame per line. Once the middle of long output is dropped, `Clip::cleaned` cleans its head and tail apart and `utils::seamed` puts the cut marker between them. `view()` is handled by the worker itself: it detects the format, writes a copy into the directory given by `SMOL_COPIES`, then sends a notification without waiting for a reply. The code runs in the worker's process and can write to its connection too, so the agent, which runs outside the sandbox, takes only a bare file name in the copies folder from that notification and reads a copy only when it is a plain file with one link. On interrupt the worker's listener thread sends `SIGINT` to the main thread, which runs the code (on Windows it raises `SIGINT` on its own thread, as Ctrl-C does there); the agent resends it every 500 ms and kills and restarts the worker if it hasn't stopped after 3 seconds.
- `crates/worker`: the embedded CPython, package `libsmol-worker`, imported as `worker`. Its build script downloads the pinned python-build-standalone build of the target into `target/pbs`, checks its checksum, links its static libpython once into `pycore.o` (on Windows it hands MSVC's linker the core's and every extension module's objects instead, with OpenSSL, libffi and rusqlite's SQLite linked statically for them) and hands libsmol the link arguments through the `links` metadata, and `pack.py` zips the standard library, with the `.pyc` stored uncompressed, into the binary. `stdlib.rs` serves that zip from memory, zipimport reading it through the open-code hook with `sys.path` naming it by libsmol's path, and `stdlib.py` hands the same bytes to what reads the stdlib as files (importlib.resources, venv's activation scripts). It exposes only `PYTHON_VERSION`, `executable()`, `program()`, the file a worker starts from, `main()`, which runs the python command line (or on Windows the venv relay) when libsmol is started by a venv's interpreter name, `isolated()`, which runs a worker's interpreter from start to finalizing, and `enter()` in `venv.rs`, which completes a venv with `venv.py` and makes that interpreter the venv's, the one place that knows how a venv is laid out. Modules built in with PyO3 go in before `isolated()`. PyO3 takes its configuration from `pyo3.cfg` without asking any Python. No crate is published on crates.io.
- `crates/smol`: the ACP client and the `smol` binary, package `libsmol-tui`. It is TUI only and exits with an error outside a terminal. `chat::Session` holds the protocol side of a session's state, and `tui/` only handles display and input. It reads no configuration, starts the `libsmol` next to it, and falls back to PATH when there is none. When the first session can't open with -32000, it runs the agent's terminal auth method in the terminal before entering the TUI, then retries once. Input starting with `!` goes through `_smol/shell`: the agent runs it with the user's `$SHELL` (cmd on Windows) in the session directory, and programs left in the background end with the session. It is recorded as `MemoryStep::Shell` and sent to the model as a user message in the next turn. Like colon commands, it queues until the current turn ends. Agents that `agent()` starts arrive as tool calls marked `_smol/agent` whose `parent` is the call running that code and whose `rawInput` holds their task, role and name, and the TUI groups them under it. All TUI colors are in `tui/theme.rs` (Dracula). On entry the TUI replaces the terminal's default foreground and background and sets a steady cursor, and it restores them on exit. Every frame is wrapped in synchronized output, and only terminals known to lack truecolor (`TERM=linux`, Apple Terminal) get 256 colors. Where it draws Kitty images (Kitty or Ghostty outside a multiplexer) it declares `_smol/images`, and libsmol then tells the model and the agents `agent()` starts to show the user an image as Markdown on a line of its own.
- `crates/reaper`: the watchdog and process groups, package `libsmol-reaper`, imported as `reaper`. However libsmol dies, the programs it started (the worker, MCP servers, `!` commands) are killed as whole groups. Programs that start a new session (`setsid`, `start_new_session`) leave the group; they are found in /proc by the `SMOL_REAPER` mark they inherit, which only works on Linux. Windows has no process groups: each program is started suspended, put in a Job Object that kills everything when its handle closes, then resumed, with no watchdog. Lookup of `.cmd` commands such as `npx` lives here too. Functions both smol and libsmol need also live here (system error text in `cause` and `described`, `terminal_view` for removing terminal escape sequences and keeping the last frame of `\r` redraws, `tilde` for writing the home directory as `~`), because smol must not depend on libsmol.

## Process

1. Look at the flow and the data first, not the files. Follow the data from a prompt coming in to the answer going out, and look for detours: one thing with two representations, two places that parse it, a layer that only forwards.
2. For a large change, write the complete plan first and start only after it is approved. The plan states the invariants (features, the shape of ACP messages, the text sent to the model), what changes and what gets deleted.
3. A claim of "no behavior change" must be proven with a black-box baseline diff: drive it with a mock model server, record the ACP message stream and the full text sent to the model, and capture the TUI with tmux screenshots. Every difference must be one the plan lists.
4. Work in phases, and at the end of each phase run `cargo fmt`, `cargo clippy --all-targets`, `cargo clippy --workspace --all-targets --target aarch64-unknown-linux-gnu` and `cargo test --workspace`.
5. The order is design refactoring, then a line-by-line readability rewrite, then cleaning up comments and tests. Done in reverse, the work gets thrown away.
6. Finish with a real model. Use deepseek for simple tasks; for long context, lower `context` in model.toml so compaction actually triggers. If the TUI changed, check it with tmux screenshots.
7. After changing code, run `./build.sh` to install `smol` and `libsmol` into `~/.local/bin` (`build.ps1` on Windows), or the user won't get the change. On Linux a running libsmol keeps starting workers from the file it runs, and on macOS its next worker starts from the new build and is refused, so restart smol. Keep build output in the project's `target/`; don't point `CARGO_TARGET_DIR` at `/tmp` (it is a RAM disk). The first build downloads about 100 MB of CPython into `target/pbs`, and linking it takes a lot of memory, so heavy builds run with `CARGO_BUILD_JOBS=2`.
8. Commit or push only when the user asks.

## Design principles

- Less code comes from putting responsibilities in the right place and deleting duplication, not from squeezing the formatting: don't widen rustfmt, don't cram expressions together, don't remove the blank lines between logical steps, don't add a flag to save a branch.
- Do each thing in one place: one parser, one representation, one error message. Prefer fewer, cohesive modules with short names free of any language's flavor.
- Put logic in the right layer. smol does not depend on libsmol, and `_smol/` extensions are added only when ACP isn't enough. A `_smol/` name means exactly one thing: the method, the marker on standard messages and the advertised capability share that name, and a key's value type never changes. Data fields use camelCase like ACP. Every `_smol/notice` carries `step` (it belongs to the step in progress) and `unsaved` (a save failed).
- libsmol reads all configuration (`model.toml`, `roles.toml`, the `[mcp.*]`, `[allow]` and `[deny]` tables in `agent.toml`) each time a session opens, so `:new` picks up changes. `libsmol setup` is the only thing that writes `model.toml`, and the format lives next to its parser in `config/`. A session that can't open for lack of `model.toml` fails with -32000 (auth required), and clients that declare ACP terminal authentication are offered `libsmol setup` as the auth method. When a session opens it also reads `AGENTS.md` (or `CLAUDE.md` when there is none) from the config directory and from every directory from the root down to the working directory, and appends them to the system prompt; files that can't be read are skipped with a notice. Skills are read at the same time: one `SKILL.md` per folder under `skills/` in the config directory and under `.smol/skills/` at every level, with deeper ones winning on a name clash. The prompt lists only `name` and `description` from the front matter plus the file path, and the model reads the file when it needs it. Roles come the same way from `roles.toml` in the config directory and `.smol/roles.toml` at every level; a role whose `model` isn't in `model.toml` is skipped with a notice, and without roles the worker (told by `SMOL_AGENTS`, which workers of agents that `agent()` starts don't get) leaves `role` out of `agent()`'s signature.
- Context in a prompt arrives as ACP resource links or embedded text, and libsmol declares embedded context so editors send what they show, unsaved edits included. A `file://` link or embedded file becomes a file attachment, read when the task starts unless its text came along, and a `#L10:20` fragment keeps only those lines. Embedded text for anything else goes to the model as `<resource uri="…">`, and other links stay in the task text.
- Errors read `label: object: problem`, all lowercase, with no trailing period. Text for people uses `Display`; text for the model lives in `prompt.rs`.
- Logs are English, one line per event, shaped `domain[qualifier]: event[, detail][ [key=value, ...]]`, lowercase with no trailing period. Lines from a session carry its id through the session's span. An error is logged once, where it ends the work it belongs to.
- Never write compatibility logic for one particular model; solve problems in the prompt or the protocol.
- Code runs only through native tool calls. Step requests declare a single `eval(code)` tool, the prompt only describes that tool, a reply without a call is the answer, and code blocks written in the message text are not run. When the tool is named `code`, models often send calls without arguments. The tool description doesn't mention tags; if it did, models would write the tags into the arguments. A call whose only argument is a string is treated as code even if that argument isn't named `code`. One reply can contain several calls; they run in order once all have arrived, and after one fails or is interrupted the rest don't run. Every call gets a reply, calls that didn't run say why, and `tool_call_id` matches each reply to its call. Calls with no readable code (another tool was called, or the eval arguments hold no code or only tags) stay in the history but don't run; they count as errors and their reply says why. Their arguments are always sent back as `{}` and characters the server rejects in tool names are replaced with `_`, so the bad content is never echoed and the server doesn't reject the request. Unreadable eval calls are mostly transient glitches, so the reply is first regenerated silently, up to 3 times, without using up error retries; only after that does each call get such a reply. In the history the code is the `tool_calls` on the assistant message, and results and errors are the `tool` messages replying to them. Images can't go in `tool` messages: once all replies of the step are sent, they go at the start of the next user message, or in a new user message when none follows, because the server rejects them in between. Call ids are numbered `call_N` in order of appearance and never change when later steps are added, which keeps the prompt cache matching. Calls in a stream arrive one after another, and each is handed over when the next one starts; once all calls have arrived, it doesn't matter how the stream ended. Each update of a call's code carries all of it, so the client gets it when it first appears and then at most every 100 ms, and all of it once the call or the stream ends. When the closing tags at the end of the code run past 256 tokens, the request is cut off and the code runs as usual (the worker strips the tags), and that step has no usage. Some models keep repeating closing tags after the code, and without the cutoff they would run to the output limit.
- The output limit is set per model with `max_tokens` in model.toml, and the provider's default applies when it is unset. deepseek counts reasoning toward it, so a small value can cut a reply off mid-reasoning. Servers may refuse a request whose input and `max_tokens` together pass the window, so compaction reserves it, up to half of what the system prompt leaves of the window, and a summary request leaves room for it. Truncated replies don't go into the history, and when the worker repairs code it keeps a copy of the original (`unrepaired`), which is not sent to the model either.
- Images and videos are enabled per model with `image` and `video` in model.toml. Whatever the current model doesn't accept is replaced with a one-line note, so the history still sends after switching models. When the model accepts neither, the system prompt doesn't list `view`, and calling it only returns that note.
- These are deliberate and must not change: the worker has no permission prompts and no network limits, there is no maximum step count, and code execution has no timeout (the user interrupts).

## Code rules

1. Code used once is not split into a function; write it where it is used so it reads top to bottom. Exceptions: trait implementations, cross-module or public APIs, recursion, functions passed as values, pure functions with their own unit tests, and helpers shared by several tests.
2. Don't pass call results or long expressions directly as arguments, as in `f(g(x), h(y)?)`; bind them to named locals first. Exceptions: constructing types and enum variants, and wrappers like `Box::new`/`Arc::new`, may be arguments or wrap a call directly; test helpers that build data, and accessors and conversions (`to_owned`, `join`, `clone` and the like), may be arguments; assert macros are exempt.
3. Leave a blank line between logical steps (setup, work, cleanup, return), and keep line length and density even.
4. Names have at most 3 words: functions, types, fields, constants and test names alike. Upper limits are `MAX_*` and lower limits `MIN_*`, with `_BYTES`, `_CHARS`, `_LINES` or `_ROWS` appended for units; waits and timeouts are `*_WAIT` and intervals `*_EVERY`; names that mirror a third-party library's parameters follow the library.
5. Always `use crate::...`, never `use super::`, in test modules too. Prefer `pub(crate)`. Don't write multi-segment inline paths in code (`std::mem::take(..)`, `crate::history::new_id()`); a single module prefix (`fs::write`, `env::var_os`) is fine.
6. Don't pass multi-line or nested closures to `map`/`map_err`/`and_then`/`ok_or_else`/`filter_map`. Use `match`, `let … else` or `for` instead, or name the mapping function first: `let failed = |e| …; .map_err(failed)?`.
7. Read each file in full before changing it, and make every change by hand, never with regex or batch replacement.
8. Check Unix and Windows `cfg` branches together; both targets must compile and be clippy-clean.

## Comments

- Write a comment only when deleting it could let a later reader silently break something: a hidden technical constraint (a panic, disk or API format compatibility, signal or thread semantics, an ordering a refactor could easily lose, a regression hit before, an ownership convention for callers).
- Don't write product or behavioral rationale, and don't write docs that restate a name, a signature or a module's purpose. If a name can say it, let the name say it.
- Write in English: one short sentence in plain, idiomatic English, starting with a capital letter and without a trailing period. Don't chain clauses with colons or semicolons, don't narrate purpose ("so that ..."), and don't paste examples.
- Use `///` on items and `//` inside function bodies. The same rules apply to Rust and to the embedded Python (`#`).
- Comments and tests the user deleted were deleted on purpose; don't add them back.

## Tests

- Tests always live in `#[cfg(test)] mod tests` inside the source file, never in a separate tests.rs. Shared helpers go in the parent module's `mod tests` as `pub(crate)`. Python helper scripts are the exception.
- Test names have at most 3 words. Assert messages print only values (`"{logs}"`), never sentences, and `expect` texts are short ("evaluate", "error").
- Test data is English. Bugs that use byte indices as character counts only show up with multibyte text, so data that goes through text handling includes accented words (café, naïve, résumé) and, where display width matters, emoji (🐍). The only Chinese in the repository is the full-width punctuation the code recognizes in model replies (such as '。' and '：') and the tests of that handling, and the text in the tests of how memories cut Chinese into words.
- Tests start real workers: the worker and python are the test binary itself, which a constructor in `lib.rs` turns into either when started as one, so worker-side code is built with `cfg(test)` too, and one venv in `target/<profile>/.venv` serves them all. Programs tests start outside the sandbox, such as the fake MCP server, run on `interpreter()`, a link named `python3` to the test binary, so tests need no Python of the machine's.

## Text for the model (prompts, builtin docs, errors)

- Priorities: accuracy first, then rules that make the model smarter, brevity last.
- Don't mention things the model shouldn't use. Whatever gets mentioned, the model drifts toward.
- Review each piece of text on its own first, then review the complete prompt as actually assembled.
- Output in examples must be captured from real runs. Builtin signatures must be exact and complete.
- In the conversation, the user's words, the code's output and the errors of running it go as they are, content from elsewhere goes in an XML tag that names it (`<file>`, `<summary>`), and everything else libsmol says goes in square brackets, such as `[no output]`, `[not run: …]` and `[The user wrote while you were working]`.
- After changing a prompt, test it with deepseek, and compare old against new when in doubt.

## Safety and configuration

- Don't change the user's real configuration (`~/.smol/`) without their consent.
- Don't print secrets: the Authorization/Cookie headers in `agent.toml` and the API keys in `model.toml`.
- When testing with a real model, copy the configuration into a temporary directory (`SMOL_CONFIG_DIR`), don't print its contents, and delete it right after. Don't write test sessions into the user's real history. The sandbox leaves the network open and most files readable, so never give a real model tasks that need accounts or secrets.
- In shell, `rm` of a variable path must be written as `"${VAR:?}"`.

## Lessons learned

- Edition 2021 has no let chains; use nested `if let` or `let … else` instead.
- A closure stored in a local and then passed as `dyn FnMut(Event)` needs its parameter type annotated (`|event: Event|`).
- Parts of rmcp's error chain don't set `source`; link them by type, then reuse `http_cause` to get the real cause.
- Python runs signal handlers only on the main thread, so the code runs there and the listener thread interrupts it with `pthread_kill`, which also wakes waits on locks (`queue.get`, `Event.wait`). On Windows it calls `raise(SIGINT)`, whose handler also sets the event that CPython's own waits watch, where `PyErr_SetInterruptEx` alone leaves `time.sleep` asleep. A long call inside a C extension that never checks signals can't be woken, and neither can a read of a pipe or socket on Windows; the only way out is the agent killing the worker.
- glibc's `system()` makes the whole process ignore `SIGINT` while it waits for the child, so `os.system` can't be interrupted, and after 3 seconds the worker is killed and every variable is lost. Interrupting `subprocess.run(..., shell=True)` kills only `sh`; the command it started is orphaned and keeps running in the worker's group until the worker is killed or the session ends.
- The worker writes the end marker before reporting in, and the agent counts it as started only after receiving both. Without this step whatever starting up prints, such as warnings from site, would count as output of the first snippet.
- While a builtin waits for the agent's reply it must release the GIL with `py.detach` and call `py.check_signals` every so often, or it can't be interrupted. The worker also waits for the next message without the GIL, so threads the code started keep running between snippets.
- python-build-standalone's static libpython is LLVM bitcode, and LTO over it in every test binary ran the machine out of memory, so the build script links it once into a native `pycore.o` with `lld -r`. The final Linux link uses lld too, since GNU ld takes archives in order and the order PYTHON.json gives misses symbols. The archive lacks the `_hacl` objects, which come from PYTHON.json's extension objects, and `+whole-archive` with `--export-dynamic` keeps every symbol the C extensions of wheels resolve at load.
- zipimport opens its archive through the open-code hook but first checks that a file is at its path, and Linux marks `/proc/self/exe` of a replaced file with ` (deleted)`, so the stdlib is named by `executable()`, which drops the mark. zipfile and importlib.resources open files with plain `open()`, so `stdlib.py` gives zipimport a reader over the same bytes and registers `as_file` for it, keeping the file names pip reads a wheel's version from. Frozen modules have no file or source, so they are off, a missing `home` gives the build machine's prefix, and stdout is lost without `Py_FinalizeEx`.
- Search paths set by hand skip CPython's own search, which also adds `PYTHONPATH`, and getpath reads `pythonpath_env` only when the environment counts, which the isolated worker turns off. So the python role reads the command line first for `-E` and `-I`, and `stdlib::search_paths` adds `PYTHONPATH` before the stdlib. venv copies its activation scripts from the folder of its `__file__`, which is inside libsmol, so `stdlib.py` gives every venv them through `importlib.resources`.
- `venv` names the interpreter's link after `sys._base_executable`, and a `libsmol` link in the venv would start the agent, so `venv.py` names it `python3`, and `enter()` sets it to the venv's python, as python run from the venv has it. libsmol takes the python role by the name it was started as, never by comparing it with its own, since macOS doesn't resolve links in `current_exe` and a copy keeps the name.
- A venv's own interpreter and `pyvenv.cfg` are files the code can replace, so the worker starts libsmol itself and becomes the venv in-process. `venv` writes `pyvenv.cfg` before it finishes, so a venv counts as complete once it has `pip`. `venv` run on an existing one restores missing links and pip in place, which keeps the folder's Landlock rule too, but leaves alone a pip that lost its script, so `venv.py` uninstalls that one first. Making a venv inside `enter()` counts toward the agent's `START_WAIT`. On macOS a subpath rule would also let the code swap a folder it writes for a link that the next session grants, so the profile keeps each one in place, and the agent replaces a link where the copies or the venv should be.
- A venv's lock file is removed only with the venv, once its working directory is gone and no session opens it again, since a session may hold the one it opened while another removes the path and makes a new file there. Its modification time is when a session last took it, which Windows lets a session set while others hold it. Windows locks are mandatory, so a held lock file is never truncated or written, and one is closed before it is removed.
- PyO3 turns `PathBuf` into `pathlib.Path`, so builtins return `OsString` where the code expects `str`.
- FTS5 gives a table a hidden column named like the table, so a column of that name fails with "vtable constructor failed". jieba cuts letters outside its own character classes, such as é, one by one, so only runs of Chinese characters go to it, and without HMM a word missing from its dictionary is cut the same way wherever it appears. Switching a new database to WAL fails at once instead of waiting when two connections do it, so the memory database keeps SQLite's default journal and writes in `BEGIN IMMEDIATE` transactions, which wait out the busy timeout. Its ids use `AUTOINCREMENT`, since SQLite otherwise hands a forgotten newest id to the next memory and an id the code still holds would delete that one.
- The code runs in a `__main__` without a file, as in the interactive interpreter, so the Python that multiprocessing starts (spawn and forkserver) can't import what the code defined, and a `Pool` waits forever on a worker that fails to load it. The worker sets `ForkingPickler.reducer_override` to refuse those functions and classes at once, with an error that says to put them in a file.
- C extensions print through C's stdio, which holds what goes to a pipe until flushed, so the worker flushes it before every end marker.
- Flushing a file waits for its lock, which a thread blocked writing to a full pipe holds and no interrupt wakes, so the worker flushes the pipes and devices the code opened on threads that the end marker waits for only 0.1 s, and regular files in line.
- A stream the code makes on fd 1 or 2 with `open(fd)` closes the fd when it is dropped, and the next file opened takes that fd and all output. So the worker writes the end marker on a copy of the pipe it took at start, and puts the pipe back on fd 1 or 2 before a snippet only when the fd is closed, never taking an fd that a file holds.
- Proxies silently close idle HTTP connections, and the worker's tokio runtime only runs during calls such as builtins, so it never sees the close and reusing the connection fails. Every HTTP client goes through `utils::http_client`, which disables connection pool reuse (`pool_max_idle_per_host(0)`).
- Landlock can only grant, never take access back below a granted folder, so a folder holding a hidden path is granted entry by entry (`spread`) and is only listed itself, which lets the code list the hidden folders below it too and make no new entries in it. A link among its entries gets no rule, since one would grant where it leads, which `/` already lets the code read. Its rules hold the inodes that existed when the session opened: the copies folder is made then and removed only when the workplace drops, and a file replaced in a spread folder becomes unreadable.
- Seatbelt takes the last matching rule and compares real paths (`/private/tmp`, not `/tmp`), so the profile is ordered by depth and every path is canonicalized. Its rules follow paths rather than folders, so renaming a folder above a hidden path would move that path out of its rule, and the profile keeps every folder above a hidden one in place.
- On macOS the worker starts through `/usr/bin/sandbox-exec -p`, by full path since `PATH` leads to the venv first, so the profile holds from the interpreter's first instruction as Landlock does, and the profile is only in its arguments, which the exec replaces. Calling `sandbox_init` in the worker would leave Python's start unconfined, and it can't run between fork and exec in libsmol, which has threads. Apple deprecated both, and without sandbox-exec the worker runs unconfined, which the log records. Site runs at start with libsmol's folder as the prefix, which `-I` keeps away from the user's site-packages, and `enter()` runs it for the venv after that and after setting `sys.prefix` and `site.PREFIXES`, because site runs the `.pth` files of the venv and reads `sys.prefix` when imported. Starting without site (`-S`) would hand the flag to the Python that multiprocessing starts, which then skips the venv's `.pth` files.
- Landlock counts connecting to a Unix socket as a write right (ABI 9, Linux 7.1), and signals and abstract sockets are scoped from ABI 6 (Linux 6.12). Older kernels drop what they don't know and the rest of the ruleset still holds, so the log names what stays open. Seatbelt checks a Unix socket by its path under `network-outbound`, and names resolve through `/private/var/run/mDNSResponder`. The profile leaves securityd reachable, so hiding `Library/Keychains` hides the files but not the items securityd hands to programs their access list trusts.
- The Landlock `pre_exec` runs after fork in a multithreaded process, so it only calls `prctl` and the raw `landlock_restrict_self` syscall, with the ruleset built beforehand in the parent.
- On Windows a DLL importing `python314.dll` binds to the main program only when the process was started from a file of that name; a copy loaded beside another program is a second, uninitialized CPython. pbs builds LTCG objects there (`cl /GL`), which only MSVC's `link.exe` reads, so lld-link and cargo-xwin can't link them, and PYTHON.json leaves out `advapi32` and `bcrypt`. pyo3-ffi links `pythonXY`, which an empty library satisfies, and its `__imp_` references resolve to the objects themselves.
- The core's `dl_nt.obj` and `_ctypes` both define `DllMain`, so `dl_nt.obj` stays out and `windows.c` defines its two globals, and `initialize()` sets `PyWin_DLLhModule`, which `sys.dllhandle` and `ctypes.pythonapi` read. `_ctypes` was built against libffi's DLL and reaches it only through `__imp_` names, which a static libffi lacks, so `windows.c` defines them; `_sqlite3` and `_ssl` call their libraries directly. openssl-src builds OpenSSL without compression, so `windows.c` also defines `COMP_get_type`, which `_ssl` refers to but never reaches, as `SSL_get_current_compression` returns NULL.
- A Windows venv's `python.exe` relays to the interpreter, so multiprocessing, which passes handles to the process it starts, must start `sys._base_executable` past the relay. The relay shares the console and ignores Ctrl-C with a handler, since ignoring it with none is inherited. PowerShell starts a program not named `.exe` through file associations and so can't run `python314.dll`, where cmd and CreateProcess can. Pythons the code starts get `PYTHONUTF8=1`, or they would write the ANSI code page to pipes the worker reads as UTF-8.
